# ADR-006: AI コーディング時代の品質・テスト戦略

**ステータス**: 採用済み
**日付**: 2026-07-04

---

## コンテキスト

このテンプレートは、コードの大半を **AI エージェント（Claude Code 等）が書く**ことを前提にしている。
AI 駆動開発には、人間中心の開発とは異なるリスクがある（2025〜2026 の業界調査で実証されているもの）:

- **AI はテストを削除/無効化してでも CI を通そうとする**（Kent Beck の証言、大規模コミット解析、
  RL モデルが `sys.exit(0)` でテストハーネスを回避した事例）。
- **"perpetually green" テスト**: AI が生成したテストはアサーションが薄く、
  ロジックを変えても通り続けることがある。カバレッジ% では検出できない。
- **AI は既存コードベースの粗を増幅する**（DORA 2025）。土台が緩いと崩れ方が速い。
- 同じツール・同じコードベースでも、**プロンプト次第で出力が大きくブレる**。

一方で AI は「手で書く手間」を厭わないため、人間時代の効率化（scaffolding 等）の価値は下がる。

本テンプレートでこの戦略を実装する過程で、**「ガードは書いてあるが実際には機能していない」**
不具合が複数見つかった（詳細は決定 5 を参照）。これは本 ADR の問題意識が抽象論ではなく、
実際に起こりうる（起こっていた）ことを裏付けている。

---

## 決定

**「生成（generation）より検証（verification）」を品質戦略の主軸に置く。**

AI が自由にコードを生成することを前提に、**逸脱したら機械的に止まる安全網（品質ゲート）を CI に埋め込む**。
「正しい骨格を生成する（push 型）」より「書かれたものが正しいかを検証する（pull 型）」に投資する。

具体的な仕組みと実行方法は [品質ゲート ガイド](../dev/quality-gates.md) を参照。本 ADR は **なぜそうするか** を記録する。

### 1. テストは層別に分け、適切な層で書く

| 層 | 役割 | DB |
|---|---|---|
| unit | ドメイン/ユースケースの純粋ロジック | 不要 |
| contract | API レスポンスのスキーマ形状 | 不要 |
| integration | 実 DB での Drizzle クエリ・制約・トランザクションの実挙動 | 必要 |
| E2E (Playwright) | ブラウザ→API→DB の通し（ハッピー＋エラー経路） | 必要 |

下層を厚く、E2E は補完（icing）。これは AI 時代でも変わらない標準原則。

### 2. カバレッジ（量）とミューテーション（質）を併用する

カバレッジ% は「実行されたか」しか見ず、**"perpetually green" を検出できない**。
ミューテーションテスト（コードにわざとバグを入れ、テストが落ちるか検証）を**質の補強層**として併用する。
実証: 本テンプレートへの導入初回実行で、`tasks`/`activity` の validators に境界値・空白トリム漏れの
survivor が複数見つかった（`< 1` を `<= 1` にしても検知できない等）。テストを追加して 100% に到達した。

### 3. ミューテーションは「純粋ロジック層のみ」に限定する

ミューテーションは**命令的ロジック向け**で、宣言的な設定・グルー（ルーティング/スキーマ/fetch/cache）は苦手。
presentation・infrastructure・client の actions/queries はミューテーションの対象外とし、
**カバレッジ + 挙動アサーション**で守る。

→ **純粋ロジック層（domain/application） = ミューテーション / グルーの多い層 = カバレッジ**という使い分け。

### 4. アーキテクチャ規約は「実効的に」強制し、二層で守る

ルールは「書いてある」だけでは無意味（実際に違反を弾けないと意味がない）。検証で確認した上で二層で強制する:

- **dependency-cruiser**: 内部レイヤ境界（`apps/` パス）＋ feature 間の直接依存禁止。
- **arch-guards（grep）**: npm パッケージレベルの禁止（domain 純粋性・framework 漏れ・検証ロジックの repo 漏れ等）。
  dep-cruiser は tsconfig paths で解決されるワークスペースパッケージや `exclude` 設定次第で
  npm パッケージへのエッジ自体を見失うため、解決に依存しない grep と併用する。

### 5. ガード自身をテストする（自己テスト）

検証ロジック（grep ガード・dependency-cruiser ルール）は**些細な書き間違いで静かに無効化されうる**。
本テンプレートへの導入時に、実際に以下の不具合が見つかった:

- `arch-guards.sh` の throw 禁止ガードが `'\\bthrow\\b'`（二重エスケープ）という正規表現バグにより、
  **一度も throw を検出できていなかった**（`config.ts` に既存の throw が 2 箇所あったことで発覚）。
- `dependency-cruiser` の feature 間直接依存禁止ルールが `to.path` で `from.path` の capture group を
  `\1` 参照する書き方をしていたが、**dependency-cruiser は from/to 間のバックリファレンスをサポートしない**
  ため、実質デッドコードだった。
- `dependency-cruiser` の `options.exclude.path` に `"node_modules"` を含めていたため、
  npm パッケージ（zod・axios・hono・drizzle-orm 等）へのエッジ自体がグラフから除外され、
  それらを禁止する複数の `to.path` ルールが**そもそも発火し得なかった**。

「既知の違反を置くと必ず落ちる」ことを検証する**ガード自己テスト**（`arch-guards.selftest.sh`）を持つことで、
この種の不具合を再発時に即座に検出できる。

### 6. テストの「存在」を CI で強制する

AI はテストを削除して CI を通そうとする。各 feature が必須の層・co-located テスト・配線を
備えているかを**構造的完全性チェック**（`feature-structure.mjs`）で機械的に検証する。
ただし feature の性質（永続化を自前で持つか、third-party SDK のラッパーか）により
必須要素は変わるため、機械的に一律要求するのではなく、リポジトリ抽象の有無・action 数などの
条件で必須要素を判定する（詳細は同スクリプトのコメントを参照）。

### 7. 依存更新の自動化と脆弱性検知を分離する

Renovate（更新 PR の作成）と `bun audit`（脆弱性の検知ゲート）は役割が異なり補完関係。両方持つ。
無人運用の事故を避けるため、自動マージは**実行に影響しない種別のみ**（devDeps/lockfile/Actions）に限定し、
本番依存はレビュー、リリースから 3 日の cooldown を置く。

## 代替案と却下理由

| 代替案 | 却下理由 |
|--------|----------|
| feature の **scaffolding ジェネレータ** | AI 駆動開発では「手コピペ」が起きないため push 型の生成は使われない。AI は正典リファレンス（`tasks`）を読んで生成する。価値は検証（pull 型）側にある |
| カバレッジ% だけで品質を担保 | "perpetually green" を検出できない。ミューテーションとの併用が必要 |
| 全層をミューテーション対象にする | 宣言的・グルーの層では survivor だらけになりノイズ。signal-to-noise が壊滅 |
| client にもミューテーションゲート | client は glue 多くノイジー。カバレッジ + 挙動アサーションで代替 |
| アーキ規約を dep-cruiser だけで強制 | npm パッケージへのエッジ解決に癖があり一部ルールが空振りしうる。grep ガードと二層で補完する |
| ガードの自己テストを省略する | 「書いてあるが機能していない」ガードを検知できない。本テンプレートへの導入時に実例が3件見つかっている |
