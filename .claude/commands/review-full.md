実装文脈を持たない read-only サブエージェント2体と、別系統のモデル（Codex CLI）1体を並列でレビューさせ、指摘がなくなるまで
「裁定 → 修正 → 修正差分限定の再レビュー」を繰り返します。引数は PR 番号（必須。例: `/review-full 94`）。

移植元: kikagaku/kikagaku-training-portal#1308 → revedge-jp/chiryonavi#1221。

## 設計の前提

**レビューはサブエージェントに任せる。** 自分が書いたコードを自分でレビューすると、実装時の判断
（「ここは意図的にこうしている」）が前提として残り、周回を増やしても同じ盲点が温存される。移植元では、
組み込み `/code-review` をインラインで3周回して見逃した不具合を、実装履歴を持たないレビューが検出した。
3周分の記録では指摘は全部1周目に出ており、2周目が拾ったのは1周目の修正が作った不整合、3周目はゼロだった。

**2体は観点が補完関係にある。** ①組み込み `/code-review`（汎用バグ、read-only）と
②プロジェクト観点（`codex-review.md` の手順と `REVIEW.md` の採否基準、**再現実験あり**）。移植元で
同一コミット・同一プロンプト・同一モデルのまま権限だけを変えて比べると、read-only 側は文書の相互参照
ずれを、再現実験側は実行時の境界条件（終了コード非伝播、未追跡ファイル、特殊なパス）を拾い、重なりが
無かった。「実際に走らせたから」見つかる部分があるので②にだけ権限を与え、①は read-only のまま残す。

**③ 別系統のモデルを1体混ぜる。** ①②は観点も権限も違うが、モデルは同じなので同じ盲点を共有する。
③は Codex CLI（`scripts/dev/codex-review.sh`）を ChatGPT のサインインで、読み取り専用の sandbox で動かす。
API キーは使わない（従量課金を避け、Plus 等のプランの枠で回す）。codex が無い・ChatGPT で未ログイン・
枠切れのときは③だけスキップして①②で続ける（スキップしたことは報告に残す）。

**レビュー中は誰もコードを触らない。** 全レビューを read-only にし、修正はオーケストレーターが
1回だけまとめて行う。並列でも行番号や前提が崩れない。

**修正は委譲しない。** 指摘の矛盾を裁定し、失敗シナリオを具体値でトレースし、規約に照らす判断が
最もコンテキストを要する。直列な1パスなのでファンアウトの利益もない。

**2周目以降は全体再レビューではなく修正差分限定。** ちりょなびの実測（同リポジトリ issue #1110）で、
2周目以降の指摘はほぼ全件が「1周目の修正が新たに生んだ回帰」だった。2周目以降は修正コミット群の
差分だけを「この修正が新たな回帰を生んでいないか」に限定して見る。

## ループ手順

### Step 0: 対象を固定する（最初に一度だけ）

```bash
mktemp -d   # 出力された絶対パスを <作業ディレクトリ> として記録する
gh pr view <PR番号> --json baseRefName,headRefName,headRefOid --jq '"\(.baseRefName) \(.headRefName) \(.headRefOid)"'
gh pr diff <PR番号> > <作業ディレクトリ>/pr<PR番号>.diff
```

**作業ディレクトリはシェル変数に入れず、絶対パスをそのまま書く。** Bash ツールは呼び出しを跨いで
シェル変数を保持しないため、`REVIEW_DIR=$(mktemp -d)` を後の呼び出しで参照すると空に展開され、
書き込みがルート直下を指す（削除に使えばさらに危険）。

**PR 番号を必ず渡す。** `/code-review` 等は `$CLAUDE_PROJECT_DIR` の現在ブランチを見るため、worktree で
実装した内容は引数無しだと**エラーにならずに別ブランチがレビューされる**（`.claude/rules/general.md`
「worktree で作業した実装のレビュー・検証」）。PR が無ければ先に Draft を作る。

差分ファイルの絶対パス・base・head の SHA を記録し、以降のサブエージェントには「レビュー対象は
このファイル」と渡す（サブエージェントに `git diff` の範囲を自分で決めさせない）。

### Step 1: サブエージェント2体と Codex を並列で起動

**1回のメッセージで2つの Agent ツールと③の Bash（`run_in_background: true`）を同時に呼ぶ**（順次呼ぶと並列にならない）。両方
`subagent_type: general-purpose`、**モデルは既定のまま**（移植元の比較で、軽いモデルはチェックリスト
は歩けるが複数ファイルを跨ぐ推論を要する指摘を落とした。チェックリストは能力を代替しない）。

**サブエージェントは親の作業ディレクトリを継承する。** worktree で作業中なら、プロンプトに
worktree の絶対パスを書き、`cd <path> && <cmd>` を毎回付けさせ、冒頭で `git log --oneline -1` の
出力を報告させて対象を確認する。

**① 汎用バグ担当（read-only）**

```
Skill ツールで code-review を実行し、結果をそのまま報告してください。
args には "medium <PR番号>" を渡してください。

- リポジトリ: <worktree の絶対パス>。コマンドはすべてそこから実行すること
- ファイルの変更は一切行わないこと（レビューのみ）
- 指摘が1件もない場合は「指摘なし」と明記すること
```

**② プロジェクト観点担当（再現実験あり）**

```
<worktree の絶対パス>/.claude/commands/codex-review.md を読み、そこに書かれた手順（Step 1〜4）
どおりにコードレビューを実施してください。採否基準はリポジトリ直下の REVIEW.md
に従うこと。ただし「ステップ0: 差分取得」は `git diff` ではなく <差分ファイルの絶対パス>
（PR #<番号> の差分）を対象にしてください。

**検証について**: 机上で読むだけでなく、疑わしい挙動は実際に動かして確かめてください。

- レビュー対象リポジトリの状態を一切変えないこと: ファイルの編集・作成（.env を含む）に加え、
  `git checkout` / `git stash` / `git reset` / `git clean` 等の git 操作も禁止（読み取りの
  `git diff` / `log` / `show` のみ可。stash スタックは全 worktree で共有されている）
- `mktemp -d` で作った一時ディレクトリの中でなら、ファイル作成・git リポジトリ作成・スクリプト
  実行など何をしても構いません。境界条件（存在しない入力、未追跡ファイル、特殊文字を含む
  パス、終了コードの伝播、set -e / pipefail の相互作用など）は、再現できるなら実際に再現して
  確かめること
- **削除操作（`rm -rf` 等）は、自分が `mktemp -d` で作ったディレクトリに対してのみ許可。
  それ以外のパスは絶対に削除しないこと**（レビュー対象リポジトリ、スクラッチパッド、
  一時ファイルの置き場を含む）
- Docker のコンテナ・volume を作る再現は、一意な名前・ポートを付けた使い捨てのものに限る
  （リポジトリの `docker compose` を main やこの worktree のプロジェクトとして起動しない）
- DB を触る再現は、.env の TEST_DATABASE_URL が指す test DB に限る（dev DB には書き込まない）
- 再現できた指摘には、実行したコマンドと観測結果を根拠として記載してください
- 指摘は 🔴 / 🟠 / 🟡 のフォーマットで、証拠（失敗シナリオ・コードパス・根拠）を必ず含めること
- 指摘が1件もない場合は「指摘なし」と明記すること
```

再現実験の権限は検出力を上げる一方、移植元では権限を与えたサブエージェントが「作業ディレクトリ整理」
のつもりで `rm -rf` を実行し、スクラッチパッドを消した実害が出ている。上の削除制約と git 操作禁止は
そのためのガードで、外さないこと。

**③ 別系統のモデル（Codex、read-only）**

```bash
cd <worktree の絶対パス> && bash scripts/dev/codex-review.sh <差分ファイルの絶対パス> <作業ディレクトリ>/codex-r1.md
```

終了コード 2 は「スキップ」（出力ファイルの先頭が `SKIPPED:` で理由付き）。③のプロンプトはスクリプトに
固定してあり、実装の文脈を足す引数は無い。③は再現実験をしない（sandbox が書き込みとネットワークを塞ぐ）
ので、③だけが出した指摘は、裁定の前にオーケストレーターが失敗シナリオをコードでトレースして確かめる。

**すべてに渡してはいけないもの（実装の文脈）:**

- この変更を何のために書いたか、どう設計したか
- 前サイクルでどこをどう修正したか
- 「ここは意図的にこうしている」等の弁明

渡すと独立性が失われ、サブエージェントが親の判断を追認するだけになる。

### Step 2: 指摘をマージして裁定する

- **重複**: 同じファイル・同じ原因の指摘は1件に統合する
- **矛盾**: 両立しない指摘は根拠の強い方を採る。判断できなければ AskUserQuestion で聞く
- **誤検知**: サブエージェントは実装文脈を知らないため、意図的な設計を誤検知する。黙って無視せず、
  根拠（コード・仕様・既存ルール）を示してユーザーに判断を仰ぐ

**裁定の結果「修正しない」と判断した指摘**は理由を添えて報告に残す:
スコープ外（別 issue を立てる）／既知のトレードオフ（テスト・文書・PR 本文に明記済み）／誤検知。

**全指摘がこの3分類に収まった場合、ループは回さずに Step 5 へ**（コードが変わっていないので
再レビューしても同じ指摘が再生産される）。報告に「修正0件・全件裁定済み」と各指摘の分類を残す。

### Step 3: 修正する（オーケストレーター自身が行う）

- 🔴 / 🟠 / CONFIRMED: 修正する
- 🟡 / PLAUSIBLE: 修正し、何をどう変えたかを1行でユーザーに通知する
- 複数ある場合は1サイクルでまとめて対処する

**充足性検証（必須）**: 指摘の「失敗シナリオ」に具体値・境界条件があれば、修正後のロジックで
その値をトレースして正しく動くことを確認する。「コードを変えた」だけで完了とみなさない。
挙動を変える修正には**反転テスト**（その修正を戻すと落ちるテスト）を付ける。

### Step 4: 回帰チェック → サイクル更新

```bash
bun run typecheck
cd apps/api-service && bun run mutation:diff   # api-service を触った場合
```

変更した feature のテストも実行する。失敗したら修正を見直し、それでも失敗するなら
AskUserQuestion で確認する。成功したらサイクル +1、修正コミットを push し、**修正差分限定の
再レビュー**を回す。先に修正差分を作る:

```bash
git diff <修正前の head SHA>..HEAD > <作業ディレクトリ>/pr<PR番号>-r<N>.diff
```

Claude のサブエージェント1体に、次のプロンプトで渡す:

```
リポジトリ: <worktree の絶対パス>。コマンドはすべてそこから実行すること。
レビュー対象は <修正差分ファイルの絶対パス>（前回指摘への修正コミット群の差分）。全体の再レビュー
ではなく「この修正が新たな回帰を生んでいないか」だけを見てください。修正前の全体差分
<差分ファイルの絶対パス> は文脈として参照可。

- レビュー対象リポジトリの状態を一切変えないこと: ファイルの編集・作成（.env を含む）、
  `git checkout` / `git stash` / `git reset` / `git clean` 等の git 操作も禁止
  （読み取りの `git diff` / `log` / `show` のみ可）
- `mktemp -d` で作った一時ディレクトリの中でなら何をしても構いません。
  **削除操作は自分が `mktemp -d` で作ったディレクトリに対してのみ許可**
- DB を触る再現は、.env の TEST_DATABASE_URL が指す test DB に限る
- 指摘は CONFIRMED / PLAUSIBLE で、失敗シナリオと再現手順を必ず含めること
- 指摘が1件もない場合は「指摘なし」と明記すること
```

前の周で③の指摘を修正したときは、同じメッセージで③も修正差分で回す（3つ目の引数で修正差分限定になる）:

```bash
cd <worktree の絶対パス> && bash scripts/dev/codex-review.sh <作業ディレクトリ>/pr<PR番号>-r<N>.diff <作業ディレクトリ>/codex-r<N>.md <差分ファイルの絶対パス>
```

これは「③の指摘が直ったかの確認」ではなく、修正差分に別系統のモデルの回帰チェックを掛けるためのもの
（③は `--ephemeral` で前の周の指摘を覚えておらず、前サイクルの修正内容も渡さない）。指摘が直ったかは
Step 3 の充足性検証でオーケストレーターが確かめる。③を回す周を「③の指摘を直した周」に絞るのは Plus 等の
枠（5 時間ごと・週ごと）を節約するためで、それ以外の周の修正差分は Claude の1体だけが見る。

**収束条件（サイクル数の上限は設けない）**

| 状態 | 判断 |
|---|---|
| 🔴 / 🟠 / CONFIRMED がある | 修正して Step 3 からやり直す |
| 🟡 / PLAUSIBLE のみ | **終了**。報告して人間に渡す（🟡 でループを回さない — 探せば無限に出る） |
| 全件「修正しない」裁定 | **終了** |
| 同一の指摘が「修正済み」を跨いで再出現 | **停止**して AskUserQuestion で方針を確認（往復ループの実検出） |

サイクル数で打ち切らないのは、深刻度と無関係な数字で切ると 🔴 を抱えたまま終わりうるため。

### Step 5: 終了報告

各サイクルで①②③それぞれが何を指摘し（③をスキップした周は理由も）、何を直したかを簡潔に残す。PR 本文末尾の2行
（`レビュー往復: N周（主な指摘: 一言）` / `レビュー収束: 最終周 CONFIRMED 0`）は `ship.md` 手順5に
従って書く。あわせて `レビュー検出: ①N ②N ③N`（全周での各レビュアーの CONFIRMED 件数。重複は全員に数え、
③をスキップした周しか無ければ `③-`）も書く — ③の効果を `bun run metrics` で測るため。**`レビュー収束:` 行が無いと必須チェック `Review converged` が通らず auto-merge が
発火しない**。「最終周」は修正差分限定の再レビューを含む最後の周を指す。作業ディレクトリは最後に、記録した絶対パスを指定して消す。

### Step 6: 観点追加の検討（ループ終了後に一度だけ）

`review-pr.md` 手順5の判定基準と手順に従う。追加先は「機械検査できる → `scripts/check/arch-guards-lib.sh`
に検査関数を足す（手順は `docs/dev/development.md`）等」「レビュー時に確認すれば足りる → `codex-review.md` の Step 3」「実装中の参照が必要かつ機械検査
できない → `.claude/rules/`」の順で判断する（`general.md` は always-loaded で肥大化しやすいので
最後の選択肢）。

---

**注意事項**

- `git commit` / `git push` は `ship.md` の運用に従う。マージはこのコマンドでは行わない
- サブエージェント2体で1サイクルあたり概ね 300k〜400k トークンを消費する（移植元実測）。
  Draft PR 作成後に1回回す運用を想定する。小さな PR（設定・文言だけ等）は `/code-review medium <PR番号>`
  で足りる。各サイクルの消費を報告し、ユーザーが判断して止められるようにすること
- ②は `codex-review.md` を読むが、モデルは①と同じ。モデルの多様性は③が担う（CI の Codex レビューは
  #86 で削除済み。③はローカル専用で、CI には置かない — `.claude/rules/agent-permissions.md`）
- ③は Plus の枠（5 時間ごと・週ごと。CLI・アプリ・Web で共有）を使う。枠の残りは `codex` の `/status`
  で確認できる
